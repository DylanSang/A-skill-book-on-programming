# Role Examples

这个文件给 10 个角色提供统一的好例子与坏例子，帮助输出更稳定。

## 通用好例子

```markdown
## 目标
让现有串口采集链路在当前板卡上稳定跑通，并给出最小回归方案。

## 已确认事实
- 当前仓库存在 `drivers/uart_bridge.c`
- `debug.json` 中记录了串口超时问题
- 板卡日志显示 open 成功但 read 超时

## 分析与判断
问题更像是驱动层收发时序或配置不匹配，而不是应用协议本身错误。

## 风险与待确认
- 波特率和流控配置尚未从板级证据中确认
- 尚未核对 DTS 中 UART 节点是否与当前驱动一致

## 建议动作 / 交付物
- 先核对 DTS、驱动 parse 和运行时配置
- 更新 `debug.json`
- 给出最小复现与回归步骤
```

特点：

- 有目标
- 有证据
- 有判断
- 有风险
- 有下一步

## 通用坏例子

```markdown
串口大概率有问题，建议检查波特率、驱动、中断、DMA、系统负载、日志和代码。
可能是 UART 配置错了，也可能是协议问题，先都看看。
```

问题：

- 没有证据
- 没有边界
- 没有优先级
- 没有可执行下一步

## 交接好例子

```markdown
## 建议动作 / 交付物
- 回填 `task-packet.json` 中的 `关键证据`：当前 DTS 节点路径、driver parse 函数、dmesg 现象
- 回填 `task-packet.json` 中的 `待确认与阻塞`：板级复位时序尚未从原理图确认
- 下一棒交给测试工程师，按最小复现步骤验证 probe 行为
```

特点：

- 不只写“建议检查”
- 明确写清要把哪些信息交回主流程
- 明确下一位接手角色

## 交接坏例子

```markdown
建议后续再继续看看，有问题再找相关同学。
```

问题：

- 没有交接字段
- 没有责任边界
- 没有下一步入口

### 产品经理

好例子重点：

- 目标用户
- 业务价值
- 验收标准
- 范围裁剪

坏例子信号：

- 只有功能列表，没有价值和验收

### 系统架构师

好例子重点：

- 责任边界
- 接口方向
- 取舍理由
- 风险与依赖

坏例子信号：

- 直接给方案图，不说明为什么这样拆

### 硬件工程师

好例子重点：

- 板级事实
- 电平 / 时序 / 复位 / 供电
- 版本适用范围

坏例子信号：

- 只说芯片支持什么，不说板上怎么接

### BSP / 驱动工程师

好例子重点：

- 文件路径
- 版本证据
- 解析链 / 匹配链
- 最小验证入口

坏例子信号：

- 只有理论说明，没有当前源码证据

### 系统 / 应用工程师

好例子重点：

- 进程或模块边界
- 配置方式
- 失败路径
- 回归入口

坏例子信号：

- 只谈主流程，不谈异常流程

### 测试工程师

好例子重点：

- 复现步骤
- 通过标准
- 阻断级别
- 回归范围

坏例子信号：

- 只罗列测试项，不给判断标准

### DevOps 工程师

好例子重点：

- 真实命令
- 环境前提
- 产物路径
- 可追溯性

坏例子信号：

- 只有流水线名字，没有本地复现路径

### 项目经理

好例子重点：

- 当前阻塞
- 关键路径
- 负责人与下一步
- 风险等级

坏例子信号：

- 只有时间表，没有依赖和风险
