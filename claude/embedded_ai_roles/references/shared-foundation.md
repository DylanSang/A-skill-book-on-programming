# Shared Foundation

这个参考文件定义所有嵌入式角色共同遵守的基础约束，避免在每个角色文件里重复硬编码同一套事实。

## 适用范围

适用于以下角色：

- 产品经理
- 系统架构师
- 硬件工程师
- BSP 工程师
- 驱动工程师
- 系统工程师
- 应用工程师
- 测试工程师
- DevOps 工程师
- 项目经理

## 共同原则

1. 证据优先
   - 用户明确约束 > 当前仓库事实 > 实测日志 > 官方文档 > 历史经验 > 模型记忆
2. 不确定就标记
   - 无法在仓库或用户输入中确认的内容，写成 `pending`、`待确认` 或 `需实现`
3. 先定义成功标准
   - 任何计划、设计、修复、测试都先写“如何判断完成”
4. 少假设，多收敛
   - 只有当业务意图不清、且错误假设成本高时，才提出最少量的澄清问题
5. 输出可交接
   - 所有产物都必须能被下一个角色继续使用，而不是只对当前上下文有意义

## 共享术语

- `workspace`: 当前工程根目录
- `evidence`: 来自仓库文件、日志、配置、脚本、输出的可引用事实
- `artifact`: 方案、Todo、debug.json、脚本、配置、测试报告等交付物
- `canonical workflow`: `.claude/embedded-feature-planner/AGENTS.md` 定义的主流程

## 共享事实边界

以下内容不要在角色文件中写死为“当前项目已确认事实”，除非角色正在处理的仓库已经证明：

- 内核版本
- RV1126 / STM32 的具体型号与外设连接
- DTS 属性和 compatible
- MQTT topic 命名细节
- 分区布局
- 工具链版本
- 构建入口

这些内容应该写成：

- 推荐检查路径
- 采证方法
- 典型风险

而不是默认真值。

## 角色输出共同要求

每个角色输出建议至少包含：

1. `目标`
2. `已确认事实`
3. `关键判断`
4. `风险/待确认`
5. `下一步`

## 禁止事项

- 不要把示例平台当成当前项目事实
- 不要把建议方案写成“系统已支持”
- 不要绕开 `.claude/embedded-feature-planner/references/evidence-and-safety.md`
- 不要在多个角色文件里复制大段完全相同的规则
