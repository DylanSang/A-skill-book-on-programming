# Task Playbooks

这个文件把最常见的嵌入式任务拆成稳定执行模板，帮助角色和主流程在真实任务中少走弯路。

## 1. 新功能规划

### 适用场景

- 新增业务功能
- 新增设备能力
- 新增系统服务
- 大版本能力扩展

### 优先加载角色

- 产品经理
- 系统架构师
- 测试工程师
- 项目经理

### 最小步骤

1. 明确目标、范围和验收标准
2. 生成 `task-packet.json`，明确角色、证据目标和验收检查项
   - 默认保持 `model_routing.disabled`
3. 判断是新工程还是已有工程
4. 若已有工程且缺少结构文档，先生成 `topStruct.md`
5. 收集当前架构、接口、版本与依赖事实
6. 汇总多角色结论
7. 输出 `方案.md`、`Todo.md`、`debug.json`

### 必查证据

- 现有模块与调用链
- 现有配置入口
- 现有构建与部署方式
- 与新功能相关的日志、接口和历史问题

### 常见误判

- 把“修现有能力”误判为“做新功能”
- 没有验收标准就开始拆任务

## 2. 编译失败 / 链接失败

### 适用场景

- `compile error`
- `undefined reference`
- `CMAKE_CXX_COMPILER not found`
- 头文件、符号、链接库问题

### 优先加载角色

- 系统工程师
- 应用工程师
- DevOps 工程师
- 测试工程师

### 最小步骤

1. 保留完整报错
2. 生成 `task-packet.json`，锁定角色和验收检查项
   - 默认保持 `model_routing.disabled`
3. 判断问题属于代码、构建脚本、工具链还是环境
4. 检查源文件是否纳入构建
5. 检查头文件、符号、链接库和 toolchain
6. 做最小修复并重编
7. 记录到 `debug.json`

### 必查证据

- 完整编译输出
- CMakeLists / Makefile / toolchain
- 相关头文件与源文件
- 链接符号来源

### 常见误判

- 只改报错行，不查构建链
- 环境问题误判成代码问题

## 3. DTS / 驱动不生效

### 适用场景

- 节点没探测到
- 属性改了无效果
- `compatible` 匹配失败
- sysfs/debugfs 节点不存在

### 优先加载角色

- 硬件工程师
- BSP 工程师
- 驱动工程师
- 测试工程师

### 最小步骤

1. 确认板级版本和当前 DTS 来源
2. 生成 `task-packet.json`，锁定角色、证据目标和交接字段
   - 默认保持 `model_routing.disabled`
3. 确认 binding 或等价约束
4. 确认 driver parse 代码
5. 确认 Kconfig / Makefile / defconfig 链路
6. 确认运行时日志或节点
7. 给出最小验证路径

### 必查证据

- DTS / DTSI
- binding 文档
- `of_device_id`
- `of_property_read_*` / `devm_gpiod_get*` / 相关 parse 函数
- dmesg / 节点输出

### 常见误判

- 只看 DTS 不看 parse
- 只看 binding 不看当前内核源码

## 4. 运行时异常 / 服务不稳定

### 适用场景

- 进程崩溃
- 死锁 / 超时
- 服务重启
- 功能时好时坏

### 优先加载角色

- 系统工程师
- 应用工程师
- 测试工程师
- DevOps 工程师

### 最小步骤

1. 收集复现条件
2. 生成 `task-packet.json`，锁定角色和回归目标
   - 默认保持 `model_routing.disabled`
3. 收集运行日志、配置、依赖状态
4. 判断属于系统服务、应用逻辑、驱动依赖还是环境问题
5. 先做最小定位，再做修复
6. 设计回归步骤

### 必查证据

- 运行日志
- 配置文件
- 启动脚本 / service 文件
- 资源占用 / watchdog / error 路径

### 常见误判

- 只看崩溃点，不看上游输入和下游副作用

## 5. 发布阻塞 / 交付前收口

### 适用场景

- 功能基本完成但无法发布
- 交付物不齐
- 测试或门禁不过
- 风险未闭环

### 优先加载角色

- 项目经理
- 测试工程师
- DevOps 工程师
- 系统架构师

### 最小步骤

1. 盘点阻塞项
2. 生成 `task-packet.json`，锁定角色、阻断项和验收检查项
   - 默认保持 `model_routing.disabled`
3. 区分阻断发布与可后移问题
4. 盘点交付物与测试证据
5. 明确负责人和最后闭环动作

### 必查证据

- 当前通过 / 未通过的门禁
- 测试结论
- 版本与产物状态
- 已知风险清单

### 常见误判

- 把“功能差不多”当成“可以发布”
- 只看代码状态，不看文档和验证状态
